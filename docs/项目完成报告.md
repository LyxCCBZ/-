## 3. 系统设计

### 3.1 总体架构

    Browser
      │ HTML 表单 / Cookie 会话
      ▼
    Flask 应用
      ├─ auth 蓝图：注册、登录、退出
      ├─ surveys 蓝图：问卷、题目、跳转、统计、JSON API
      ├─ public 蓝图：公开链接、逐题填写、答卷保存
      ├─ services：校验、跳转、统计
      └─ PyMongo
            ▼
    MongoDB 8
      users / surveys / questions / responses

系统采用服务端渲染，减少前端复杂度，同时把关键逻辑放在服务端：

- 页面只负责展示和收集输入。
- 答案校验、跳转判断、状态流转、权限判断全部由 Flask 完成。
- MongoDB 负责持久化、唯一约束、Schema 校验和统计聚合。

### 3.2 页面与交互

1. 注册/登录页：建立账号会话。
2. 我的问卷：按创建时间显示当前用户问卷和提交数。
3. 新建问卷：创建 draft。
4. 问卷管理页：设置、题目列表、跳转配置、公开链接、发布/关闭。
5. 公开说明页：登录后开始填写。
6. 单题填写页：根据题型显示 radio、checkbox、textarea 或 number 输入。
7. 提交成功页：确认答卷已保存。
8. 统计页：整卷或单题统计，含条形比例和数字汇总。

### 3.3 问卷状态机

    draft ──发布──> published ──主动关闭/到期──> closed

- draft 可编辑题目、删除题目、配置跳转。
- published 可填写，题目结构锁定，设置可调整。
- closed 不再接受新答卷。

## 4. MongoDB 设计

### 4.1 集合拆分

| 集合 | 作用 | 关键索引 |
| --- | --- | --- |
| users | 账号与密码哈希 | username 唯一 |
| surveys | 问卷元数据、状态、公开编号 | public_id 唯一；owner_id + created_at |
| questions | 题目、选项、校验、跳转 | survey_id + order 唯一 |
| responses | 每次填写、答案、提交状态 | survey_id + status；single_response=true 时 survey_id + respondent_key 唯一 |

没有把所有内容放进一个集合，也没有把每道题的答案拆成大量行。

### 4.2 引用与内嵌

- survey.owner_id 引用 user。
- question.survey_id 引用 survey。
- response.survey_id 引用 survey。
- response.answers.question_id 引用 question。
- answers 内嵌在 response，因为答卷是一个整体聚合根。
- jumps 内嵌在 question，因为规则数量少且总随题目读取。
- 选项文字只保存在 question.options，答案只保存 key，避免重复冗余。

### 4.3 为什么适合 MongoDB

- 不同题型有不同 validation 子文档，文档模型天然支持可变结构。
- 跳转规则是题目的子数组，不需要额外 join 表。
- 一份答卷的多题答案可以一次读取，统计时使用 unwind/group。
- 四个集合职责清楚，索引独立，避免单集合万能表。

### 4.4 数据完整性

- 四个集合配置 $jsonSchema，validationAction=error。
- 用户名、public_id、survey_id+order 建唯一索引；单次问卷通过部分唯一索引阻止同一用户并发创建多份答卷。
- 发布后锁定题目结构，保护已有答卷。
- 删除题目时清理相关跳转。
- 答案写入前做服务端校验。

更详细的字段、示例和设计权衡见 docs/数据库设计.md。

## 5. 条件跳转设计

题目文档保存 jumps 数组：

    [
      { "condition": { "operator": "eq", "value": "A" },
        "target_question_id": "ObjectId 或 END" }
    ]

配置阶段：

- 目标只能是后续题目或 END。
- 条件必须匹配题型，例如多选使用 includes_any/includes_all/not_includes。
- 选项条件引用稳定的 A/B/C key。

运行阶段：

1. 校验当前答案。
2. 按数组顺序检查条件。
3. 第一条命中规则生效。
4. 目标为 END 则提交；否则跳转到目标题。
5. 无规则命中则进入下一题。

这样跳转逻辑完全由数据驱动，修改问卷时不需要修改 Python 代码。

## 6. 校验设计

| 题型 | 校验 |
| --- | --- |
| 单选 | 选项存在；必答时不能为空 |
| 多选 | 去重；选项存在；必答；min/max 数量 |
| 文本 | 去首尾空格；必答；最小/最大字符数 |
| 数字 | 可解析；范围闭区间；可选只允许整数 |

浏览器端 required/min/max 只是第一层提示，真正的校验在 services/validation.py 执行。校验失败返回 422，保留用户原输入，不写入答案。

## 7. 答卷流程与匿名设计

开始答卷时创建 response，状态 in_progress。每答一题立即更新 answers 和 current_question_id。到达 END 后改为 submitted，记录 submitted_at。

访问控制：

- 公开链接使用随机 public_id。
- 开始答卷生成随机访问令牌，原始令牌在签名会话中，数据库保存 SHA-256 哈希。
- 没有令牌无法查看或修改答卷。

匿名：

- allow_anonymous=true 时，填写者可以选择匿名。
- 匿名答卷不保存 respondent_id。
- 为兼顾“禁止重复提交”，保存 respondent_key = HMAC(secret, survey_id + user_id)。它不可逆、不展示，仅用于去重。

## 8. 统计设计

统计只读取 submitted 答卷。MongoDB 聚合步骤：

- $match：survey_id 且 status=submitted。
- $unwind：展开 answers。
- $group：按 question_id 收集 value。

应用层再按题型计算：

- 单选：每个选项人数与百分比。
- 多选：每个选项被选择次数与百分比。
- 文本：全部填写内容。
- 数字：平均值、最小值、最大值。

因为分母是该题实际回答人数，跳过该题的填写者不会影响比例。

## 11. 遇到的问题与解决

### 11.1 需求中的“三种题型”和“填空题有文本/数字两种”

处理：数据库使用 single、multiple、text、number 四种 type，把文本和数字视为填空的两种控件。这样更利于统计和校验，仍覆盖三类题型要求。

### 11.2 跳转可能导致循环

处理：只允许跳到后续题目或 END，从数据层禁止回跳。

### 11.3 发布后题目变化与旧答卷冲突

处理：发布后锁定题目和跳转结构。第一阶段不支持修改已发布题目，避免答案引用失效。

### 11.4 匿名与重复提交限制冲突

处理：不保存 respondent_id，但保存不可逆 respondent_key 执行去重。统计和界面均不展示该键。

### 11.5 截止时间需要自动生效

处理：在管理页、公开页、答卷页读取问卷时检查 deadline，过期就把 published 原子更新为 closed，不依赖定时任务。

### 11.6 统计页字段名冲突

处理：模板中 item.values 被解析为字典方法，改名为 answer_values 后解决。

### 11.7 并行草稿可能绕过重复提交限制

处理：`allow_multiple=false` 时，开始填写前同时检查已提交答卷和未完成答卷。同一会话可以继续原答卷，其他会话不能新建第二份草稿。

### 11.8 登录后的 next 参数存在反斜杠重定向风险

处理：站内跳转校验拒绝反斜杠和控制字符，外部地址、协议相对地址和异常路径统一回到“我的问卷”页面。

### 11.9 非有限数字可能进入业务数据

处理：答案校验、题目数字范围和数字跳转条件统一使用有限数检查，拒绝 `NaN`、`Infinity` 和溢出浮点值。

### 11.10 草稿关闭接口提示与实际状态不一致

处理：关闭接口明确区分 draft、published 和 closed 状态，草稿状态不允许关闭。

## 12. 第一阶段限制与第二阶段扩展方向

第一阶段当前限制：

- 题目发布后不能修改，只支持草稿添加/删除。
- 没有题目拖拽排序和题目编辑表单。
- 没有 CSRF Token、登录限流、HTTPS 配置。
- 超大问卷统计未分页。
- 禁止重复填写已由 MongoDB 部分唯一索引兜底；登录限流和应用级防刷仍未实现。
- 题目删除只用于草稿。

第二阶段扩展建议：

1. 需求加入“修改已发布题目”时，增加 question_version 或 answer_snapshot，保留旧答卷语义。
2. 保留现有 users/surveys/questions/responses 主结构，通过新增字段和集合扩展，不推倒重做。
3. 若增加问卷模板、协作编辑、配额或导出，新增独立集合，避免过度内嵌。
4. 若增加复杂统计，增加预聚合集合或按需缓存。
5. 若增加匿名强度，取消基于 HMAC 的重复限制或改用一次性邀请码。
