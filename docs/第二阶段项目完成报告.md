## 1. 阶段目标

第二阶段依据《大作业一：需求变更.docx》在既有系统上增量实现题库与题目版本管理，不移除、不重写第一阶段已经验收的问卷创建、填写、跳转、校验、统计和隐私控制。

需求变更包含八项要求：

1. 保存常用题目，创建新问卷时可选用，一道题可被多份问卷使用。
2. 把题目共享给其他用户，对方可在自己的问卷中使用。
3. 修改题目不得影响已有问卷；已发布问卷中的题目不可修改。
4. 记录题目历史版本，可查看版本关系并恢复旧版本。
5. 同一题目的多个版本可同时存在，不同问卷可使用不同版本。
6. 查看某道题被哪些问卷使用，修改时决定是否创建新版本。
7. 建立题库，支持管理、添加题目、从题库选题和更新版本。
8. 支持跨问卷查看同一道题的统计结果。

## 3. 总体设计

### 3.1 三层题目模型

    逻辑题目 question_bank
      ├── current_version_id / current_version
      ├── shared_with
      └── 不可变版本 question_versions
              └── 被复制到 questions（问卷使用快照）

- question_bank：题目的逻辑身份、所有者、当前版本指针、共享用户。
- question_versions：题目在某个时刻的完整内容，插入后不再修改。
- questions：问卷实际使用的题目快照，继续承担填写、跳转、校验和问卷内统计。

### 3.2 为什么保留 questions 快照

第一阶段的 questions 是发布即锁定的结构，responses.answers 只保存 question_id 与选项 key。如果第二阶段让问卷实时读取题库最新版本，改题会改变旧问卷的题干和选项含义，历史答卷将无法解释。

因此系统采用“选题即复制”：从题库选择版本时，把 title、type、required、options、validation 复制进 questions，并记录 library_question_id、library_version_id、library_version_number、library_owner_id。题库后续改版只影响新的选题，不触碰已有问卷。

该方案同时满足：

- 旧问卷内容与旧答案稳定。
- 不同问卷可使用不同版本。
- 已发布问卷仍然禁止修改题目。
- 跨问卷统计仍可通过 library_question_id 找到所有使用快照。

### 3.3 版本创建与恢复

- 创建版本：校验内容，计算 max(version_number)+1，插入新版本，更新 question_bank 当前版本指针。
- 唯一索引 bank_id + version_number 防止并发重复；冲突时应用层重试。
- 恢复版本：复制目标历史版本内容创建新版本，parent_version_id 指向当前版本，restored_from_version_id 记录来源版本。
- 恢复不会删除 v2、v3 等中间版本，版本号单调递增，历史链完整。

### 3.4 权限模型

| 操作 | 所有者 | 被共享用户 | 其他用户 |
| --- | --- | --- | --- |
| 查看题目详情 | 允许 | 允许 | 404 |
| 在自己的草稿问卷中选题 | 允许 | 允许 | 不允许 |
| 创建版本 / 恢复版本 | 允许 | 403 | 404 |
| 共享 / 取消共享 | 允许 | 403 | 404 |
| 复制为自有题目 | 不适用 | 允许 | 不允许 |
| 查看使用情况 | 全部问卷 | 仅自己创建的问卷 | 无 |
| 查看跨问卷统计 | 全部问卷 | 仅自己创建的问卷 | 无 |

共享不会授予对方修改原题或查看他人问卷统计的权限。

### 3.5 跨问卷统计口径

1. 以 library_question_id 查询所有相关 questions 快照。
2. 若查看者不是所有者，只保留其自有问卷。
3. 只统计 status=submitted 的答卷。
4. 按 answers.question_id 取值，分别计算每份问卷、每个版本和总体的回答量。
5. 选择题总体统计以 `(选项 key, 选项文本)` 为键，避免不同版本同编号含义不同被错误合并。
6. 数字题汇总平均值、最小值、最大值；文本题最多展示 200 条。

### 8.1 AI 帮了什么

- 扩展 MongoDB Schema 与索引，新增 question_bank、question_versions，并为 questions 增加 library_* 关联字段。
- 生成题库服务层、路由、四个页面模板和第二阶段自动化测试。
- 生成演示数据、README、数据库设计、API 说明、系统说明、关键逻辑说明和测试用例的更新初稿。
- 根据全量测试与演示数据运行结果，定位并修正实现问题。

### 8.2 AI 做错了什么、如何修正

- 初始只修改了 db.py 的 Schema，没有服务层、路由、模板和测试，功能并未闭环；随后补齐完整实现链路。
- 第一次提交题库创建请求返回 405，因为只实现了 `POST /question-bank/new`，缺少 `POST /question-bank`；补充路由并复用同一创建逻辑。
- 实现“复制为我的题目”时，创建函数只接受表单格式，而复制得到的是已解析的选项数组；补充 `create_bank_from_content`，统一两种入口。
- 题目使用情况中，所有者看到他人问卷时链接仍指向仅所有者可访问的问卷统计页；改为非自有问卷只显示标题、不生成链接。
- 权限检查最初对未共享用户返回 403，可能暴露题目存在；改为先判断访问权，未授权统一 404，仅被共享用户的越权管理返回 403。
- 版本并发重试时父版本可能使用旧的当前版本指针；改为每次重试重新读取 question_bank 的当前版本。

### 8.3 自己改了什么

- 决定保留第一阶段 questions 作为问卷题目快照，不改写公开填写、答案校验、跳转和问卷内统计。
- 确定“逻辑题目 + 不可变版本 + 问卷快照”的增量方案，并据此调整数据库和页面流程。
- 确定共享用户只能查看自己问卷范围内的使用情况与统计，避免共享成为窥探他人数据的入口。
- 确定跨问卷选择题按“选项编号 + 选项文本”合并，避免不同版本同编号含义不同被错误统计。
- 执行全量测试、连续两次演示数据导入、压缩包解压后回归测试，并核对页面渲染结果。

### 8.4 自己设计了什么

- 三层题目模型：question_bank 保存逻辑身份与当前版本指针，question_versions 保存不可变内容，questions 保存问卷实际使用的版本快照。
- 版本链设计：parent_version_id 表达正常演进，restored_from_version_id 区分恢复操作；恢复旧版本时复制内容生成新版本，历史不删除。
- 共享与复制设计：所有者可共享和改版，被共享用户可选题和复制为自有题目，既支持协作又保留各自修改权。
- 跨问卷统计设计：以 library_question_id 聚合题目快照，按问卷、版本、总体三层汇总，并按查看者权限裁剪统计范围。
- 发布锁定与快照隔离的组合：既满足改题不影响旧问卷，也保留第一阶段“已发布问卷不可改题”的数据保护策略。

## 9. 已知限制与后续可扩展点

- 题库题目暂未提供删除或归档功能；如需删除，应先检查使用情况并设计软删除。
- 草稿问卷换版需要删除旧题后重新从题库选择，暂未提供“一键切换版本”。
- 共享只支持按用户名逐个添加，暂未提供团队/角色和链接分享。
- 跨问卷文本统计最多展示 200 条，未实现分页与导出。
- 未实现题库标签、搜索、排序和批量导入导出。
- CSRF Token、HTTPS、登录限流等生产加固仍未包含在课程作业范围内。

以上限制不影响本次需求变更的验收项。
