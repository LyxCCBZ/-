# 关键逻辑说明

## 1. 条件跳转

### 1.1 数据结构

跳转规则保存在 question.jumps 数组中。每条规则包含：

- condition.operator：条件类型。
- condition.value：条件值，可能是选项编号、编号数组、数字或区间。
- target_question_id：目标题目的 ObjectId，或字符串 END。

规则按数组顺序保存，顺序就是优先级。

### 1.2 保存时校验

添加规则时执行以下检查：

1. 当前问卷必须是 draft，避免发布后改变已有结构。
2. 当前题目必须属于该问卷。
3. 目标必须是当前题目之后的题目，或 END。
4. 条件操作符必须与题型匹配。
5. 条件值必须引用本题目真实存在的选项，或能被解析为数字/区间。

只允许向前跳转可以从结构上避免 A→B→A 的死循环，也符合“按顺序回答”的需求。

### 1.3 运行时算法

每一题提交后：

    读取当前题目和标准化答案
    for rule in current_question.jumps:
        if matches(rule.condition, answer):
            if rule.target_question_id == "END":
                return END
            return 目标题目
    return 下一道 order 更大的题目
    如果没有下一题，返回 END

只执行第一条命中的规则。未命中跳转规则时使用默认顺序，不需要为“默认下一题”单独配置规则。

### 1.4 条件匹配

- 单选：answer 是一个选项 key，直接比较。
- 多选：answer 是 key 数组。
  - includes_any：交集非空。
  - includes_all：条件集合是答案集合的子集。
  - not_includes：交集为空。
- 数字：转 float 后比较；between 使用闭区间。
- 文本：使用字符串包含或相等比较。

跳转条件保存在 MongoDB 中，程序只实现通用的匹配器，不包含针对具体问卷的 if/else，因此满足“不把跳转写死在程序里”。

## 2. 答案校验

### 2.1 单选

- 有值时必须属于该题 options 的 key 集合。
- required 且为空时报错。
- 非必答允许空值。

### 2.2 多选

- 去重后保存。
- 每个 key 必须属于该题选项。
- required 时至少选择一个。
- min_select 与 max_select 同时生效。
- 值保存为数组，例如 ["A", "C"]。

### 2.3 文本

- 去除首尾空格。
- required 时不能为空。
- 长度按 Python 字符数计算。
- min_length 与 max_length 同时生效。

### 2.4 数字

- 使用 float 解析，非法文本立即报错。
- integer_only 时检查 number.is_integer()。
- minimum / maximum 为闭区间。
- 整数结果保存为 int，小数保存为 float。

校验在服务端完成，浏览器端的 required、min、max 只用于改善体验，不能替代服务端校验。

## 3. 逐题填写与草稿保存

系统没有把整张问卷一次性提交，而是采用“单题请求 + 服务端跳转”的方式：

1. 开始答卷时创建 response，status=in_progress，current_question_id=第一题。
2. 用户提交当前题，服务端校验答案。
3. 将答案加入 answers；如果同一 question_id 已有答案，则替换。
4. 计算下一题，更新 current_question_id。
5. 如果到达 END，status=submitted，submitted_at=当前时间。

每次有效作答都是一次 MongoDB 更新，因此中途退出后已经提交的题目已经保存。用户当前停留在哪一题也由服务端记录，不依赖前端状态。

## 4. 答卷访问控制

开始答卷时：

- 生成 secrets.token_urlsafe(32) 随机令牌。
- 把令牌原文放入用户签名会话的 attempt_tokens 映射。
- 把 SHA-256 哈希写入 response.access_token_hash。

访问 /attempt/ID 或提交答案时：

1. 从会话中取出该答卷的令牌。
2. 计算哈希。
3. 与数据库中的 access_token_hash 做恒定时间比较。
4. 不匹配则返回 404。

这样即使他人猜到 ObjectId，也不能操作别人的答卷。令牌不放在 URL 中，避免出现在浏览器历史和转发链接里。

## 5. 匿名与去重

需求同时要求“匿名填写”和“同一个人填写多次（如果允许）”。系统采用以下折中：

- allow_anonymous=true 时，填写者可选择匿名。
- 匿名答卷不保存 respondent_id。
- 但始终保存 respondent_key：
      HMAC-SHA256(SECRET_KEY, survey_id + ":" + user_id)
- allow_multiple=false 时，用 respondent_key 查询该问卷是否已有 submitted 答卷。
- respondent_key 不可逆，不在页面或统计中显示，只用于唯一性判断。

因此匿名表示“后台不记录可读身份”，而不是完全无法执行重复提交限制。若要求绝对不可关联，应取消匿名模式下的重复限制，或使用一次性匿名凭证。

## 6. 发布、关闭与截止时间

状态机：

    draft ──发布成功──> published ──主动关闭或到期──> closed

- draft：可添加/删除题目、配置跳转。发布要求至少一题。
- published：可填写；题目与跳转结构锁定；可调整标题、说明、截止时间；可关闭。
- closed：不能开始新答卷，不能修改设置。

每次读取问卷时检查 deadline；若已过期且状态仍为 published，就原子更新为 closed 并记录 closed_at。这个检查发生在管理页、公开页和答题页，避免依赖后台定时任务。

正在填写但尚未提交的答卷，如果问卷关闭，会看到关闭页面，不继续接受答案；已保存的草稿仍保留在数据库中。

## 7. 重复填写限制

allow_multiple=true：同一账号可以发起多份答卷。  
allow_multiple=false：开始答卷前按 survey_id + respondent_key 查询已提交答卷，存在则拒绝。

匿名模式仍使用 respondent_key，因此可以阻止同一账号的第二次提交。系统只禁止“已提交”的重复，不阻止同一用户拥有多个未完成草稿；这样可以允许多个浏览器标签同时填写，最后以各自答卷独立存在。

## 8. 统计逻辑

统计只读取 status=submitted 的 response。

MongoDB 聚合：

1. $match：survey_id 匹配且 status=submitted。
2. $unwind：展开 answers 数组。
3. $group：按 answers.question_id 分组，把 value 收集成数组。

随后在应用层按题型解释：

- 单选：每个答案是一个 key，对选项计数。
- 多选：每个答案是 key 数组，对数组内的 key 累加。
- 文本：直接输出全部值。
- 数字：过滤数值，求平均、最小、最大。

百分比以“回答该题的人数”为分母，不包含因跳转未看到该题的人。这样跳转问卷的选项比例不会被跳到该题之外的人稀释。

## 9. 数据一致性措施

- 发布后锁定题目，避免题目结构与已有答案不一致。
- 删除草稿题目时，同时删除所有指向它的跳转规则。
- 题目 order 由 max(order)+1 生成，唯一索引避免重复。
- 问卷归属检查在每次管理请求执行，不依赖前端隐藏按钮。
- 开始答卷前检查状态、截止时间、重复提交。
- 答案校验失败不会写入 answers。
- 提交时使用 status=in_progress 作为更新条件，避免已提交答卷被晚到的请求覆盖。

## 10. 并发与边界

多人同时填写是安全的：每个填写者对应独立 response 文档，写入不同文档，不会互相覆盖。

同一份答卷被重复提交时，最后一次请求可能覆盖同一题答案，但不会影响其他答卷。若需要严格的“单次提交”语义，可在第二阶段为 question_id 使用数组过滤器或增加版本号。

当前限制：

- 没有 CSRF Token；部署到公网前应增加。
- 重复提交检查是查询后插入，极端并发下可能同时通过；可通过参与记录和唯一索引加固。
- 问卷发布后不支持直接修改题目；题库改版通过新增不可变版本实现，已有问卷继续使用自己的快照。
- 没有分页展示超大文本统计；第一阶段数据量较小。

## 11. 题库版本与问卷快照

### 11.1 三层数据

    逻辑题目 question_bank
        ├── 当前版本指针 current_version_id / current_version
        ├── 共享用户 shared_with
        └── 不可变版本 question_versions（v1、v2、v3……）
                └── 被复制为 questions 中的问卷题目快照

question_bank 表达“这是同一道题”；question_versions 表达“这道题在某个时刻的内容”；questions 表达“某份问卷实际使用的题目”。

### 11.2 创建版本

“修改题目”不更新旧版本文档，而是：

1. 校验表单，得到标准化的 title、type、required、options、validation。
2. 读取当前最大 version_number，计算新版本号。
3. 插入新的 question_versions 文档，parent_version_id 指向当前版本。
4. 更新 question_bank 的 current_version_id、current_version、title、type、updated_at。

如果 bank_id + version_number 唯一索引发生冲突，重试计算版本号，避免并发下产生重复版本。

### 11.3 恢复历史版本

恢复 v1 不会把 current_version 指回 v1，也不会删除 v2、v3。系统复制 v1 的内容创建 v4，并写入：

    parent_version_id = 当前版本 v3
    restored_from_version_id = v1

因此历史链保持单调递增，既能看到“恢复自哪个版本”，也不会丢失中间版本。

### 11.4 从题库选题

从题库选题时，服务端按 version_id 读取指定版本，把内容复制到 questions：

    survey_id、order
    library_question_id、library_version_id、library_version_number、library_owner_id
    title、type、required、options、validation
    jumps = []

后续填写、跳转、校验和问卷内统计全部读取 questions，不实时读取题库。因此：

- 题库创建 v2 不会改变使用 v1 的旧问卷。
- 不同问卷可以分别使用 v1、v2。
- 已发布问卷仍然锁定 questions，不能换题或删除。
- 草稿问卷如需换版，删除旧题后重新从题库选择目标版本。

### 11.5 权限判断

    can_access(bank, user) = user == owner_id or user in shared_with
    can_manage(bank, user) = user == owner_id

详情与统计使用 can_access；创建版本、共享、取消共享使用 can_manage。被共享用户复制题目时，系统以其当前版本内容创建一个全新的 question_bank 与 v1，之后与原题完全独立。

## 12. 跨问卷题目统计

### 12.1 查找范围

1. 在 questions 中查找 library_question_id = 目标题库题目的全部题目快照。
2. 根据快照的 survey_id 找到所属问卷。
3. 所有者保留全部问卷；被共享用户只保留 owner_id = 当前用户的问卷。

这样共享题目不会成为查看他人问卷统计的入口。

### 12.2 取值与汇总

对范围内问卷执行与问卷内统计相同的聚合：

    $match: survey_id in 范围内问卷, status = submitted
    $unwind: answers
    $group: by answers.question_id, push value

然后按题目快照的 _id 取回答值，因为同一道题在不同问卷中的 question_id 不同：

- 每个快照单独计算回答数、选项计数、数字均值/最值。
- 同一版本的多份问卷再按版本汇总。
- 全部版本再汇总总体选项分布与数字统计。

### 12.3 选项合并规则

不同版本中 A 选项可能代表不同含义，因此总体选项统计以 `(key, text)` 为键，而不是只用 key。若 v1 的 A 是“满意”、v2 的 A 是“非常满意”，统计页会显示两行，避免错误合并。

百分比分母是该范围内回答该题的次数；跳转导致未看到题目的填写者不计入分母。

### 12.4 统计口径

- 只统计 status=submitted 的答卷。
- 同一道题在多份问卷中分别计数，再跨问卷汇总。
- 文本回答最多展示 200 条，避免页面过大。
- 问卷内统计与跨问卷统计互不影响：前者只看单份问卷，后者按题目身份聚合。
