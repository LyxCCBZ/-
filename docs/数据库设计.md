# 数据库设计

## 1. 设计目标

MongoDB 设计需要同时满足以下要求：

- 支持不同题型各自不同的配置项。
- 支持题目级别的多条条件跳转规则。
- 保证用户只能访问自己的问卷。
- 支持公开链接、截止时间、匿名、重复填写限制。
- 支持答卷逐题保存和自动统计。
- 避免把所有数据堆进一个集合，避免不必要的冗余。

系统使用一个数据库 questionnaire_phase1，包含六个集合：users、surveys、questions、responses、question_bank、question_versions。后两个集合是第二阶段为题库、共享和题目版本化新增的。

## 2. 集合关系

    users 1 ─── N surveys 1 ─── N questions
                         │
                         └─── N responses N ─── 1 questions（answers 中的引用）

    users 1 ─── N question_bank 1 ─── N question_versions
                        │
                        └─── N questions（通过 library_question_id / library_version_id 记录使用快照）

关系通过 ObjectId 引用实现：

- surveys.owner_id → users._id
- questions.survey_id → surveys._id
- responses.survey_id → surveys._id
- responses.answers.question_id → questions._id
- responses.respondent_id → users._id；匿名答卷为 null 或不保存实际身份
- question_bank.owner_id → users._id
- question_bank.shared_with → users._id 数组
- question_versions.bank_id → question_bank._id
- questions.library_question_id → question_bank._id
- questions.library_version_id → question_versions._id

MongoDB 不提供跨集合外键约束，应用层与 Schema Validator 共同保证字段类型和必填约束。

## 3. users 集合

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| _id | ObjectId | 用户主键 |
| username | string | 用户名，小写规范化，3-30 位 |
| password_hash | string | scrypt 哈希，不保存明文 |
| created_at | date | 注册时间 UTC |

索引：

    { username: 1 } unique

设计理由：用户数据量小、字段稳定；账号只需要按用户名登录查询，因此单独集合并使用唯一索引。

## 4. surveys 集合

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| _id | ObjectId | 问卷主键 |
| public_id | string | 公开链接随机编号，唯一 |
| owner_id | ObjectId | 创建者 |
| title | string | 标题，1-200 字 |
| description | string | 说明，最多 2000 字 |
| allow_anonymous | bool | 是否允许匿名提交 |
| allow_multiple | bool | 是否允许同一账号重复提交 |
| status | enum | draft / published / closed |
| deadline | date 或 null | 截止时间 |
| created_at | date | 创建时间 |
| updated_at | date | 更新时间 |
| published_at | date 或 null | 发布时间 |
| closed_at | date 或 null | 关闭时间 |

索引：

    { public_id: 1 } unique
    { owner_id: 1, created_at: -1 }

设计理由：

- public_id 与 _id 分离，公开链接不暴露数据库主键，也便于重新生成。
- status 与 deadline 分离：status 由创建者动作或系统超时共同决定，保留可审计的发布时间与关闭时间。
- 所有者加创建时间的复合索引支持“我的问卷列表”按时间倒序查询。

## 5. questions 集合

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| _id | ObjectId | 题目主键 |
| survey_id | ObjectId | 所属问卷 |
| library_question_id | ObjectId 或 null | 来源题库题目；问卷内直接创建的题目为 null |
| library_version_id | ObjectId 或 null | 来源题库版本 |
| library_version_number | int 或 null | 来源版本号，便于列表展示 |
| library_owner_id | ObjectId 或 null | 题库所有者，便于权限判断与审计 |
| order | int | 问卷内顺序，从 1 开始 |
| type | enum | single / multiple / text / number |
| title | string | 题目内容，最多 300 字 |
| required | bool | 是否必答 |
| options | array | 选择题选项，元素为 {key, text} |
| validation | object | 题型相关校验配置 |
| jumps | array | 条件跳转规则 |
| created_at | date | 创建时间 |
| updated_at | date | 更新时间 |

validation 示例：

    单选：{}
    多选：{ min_select: 2, max_select: 3 }
    文本：{ min_length: 3, max_length: 100 }
    数字：{ minimum: 0, maximum: 120, integer_only: true }

jumps 示例：

    [
      {
        condition: { operator: "eq", value: "A" },
        target_question_id: ObjectId("...")
      },
      {
        condition: { operator: "neq", value: 18 },
        target_question_id: "END"
      }
    ]

索引：

    { survey_id: 1, order: 1 } unique
    { library_question_id: 1 }
    { library_version_id: 1 }

设计理由：

- 题目作为独立集合，而不是全部嵌入 surveys：题目数量可变，且需要按 survey_id 独立查询、统计和第二阶段扩展。
- validation 使用可变子文档，避免为每种题型建立大量稀疏字段。
- options 只在选择题出现；选项 key 稳定，答案只保存 key，不重复保存选项文字。
- jumps 内嵌在题目中，因为跳转规则天然属于某道题，读取题目时一并读取；规则数量通常很小，嵌入比单独集合更高效。
- survey_id + order 唯一索引保证题目顺序不重复，并支持按顺序快速读取。
- 从题库选题时，把指定版本的完整内容复制到 questions，形成不可变使用快照；library_* 字段只用于追溯来源和跨问卷统计，不参与填写时读取题库最新内容。

## 6. responses 集合

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| _id | ObjectId | 答卷主键，也是答题访问 ID |
| survey_id | ObjectId | 所属问卷 |
| respondent_id | ObjectId 或 null | 非匿名填写者；匿名时不保存实际身份 |
| respondent_key | string | HMAC 去重键，不可逆 |
| access_token_hash | string | 随机访问令牌的 SHA-256 |
| single_response | bool | 是否属于“禁止重复填写”的问卷，用于数据库唯一约束 |
| is_anonymous | bool | 是否匿名 |
| answers | array | 内嵌答案快照 |
| status | enum | in_progress / submitted |
| current_question_id | ObjectId 或 null | 服务端当前题目 |
| started_at | date | 开始时间 |
| submitted_at | date 或 null | 提交时间 |

answers 示例：

    [
      { question_id: ObjectId("..."), value: "A", answered_at: ISODate("...") },
      { question_id: ObjectId("..."), value: ["A", "C"], answered_at: ISODate("...") },
      { question_id: ObjectId("..."), value: 25, answered_at: ISODate("...") }
    ]

索引：

    { survey_id: 1, status: 1 }
    { survey_id: 1, respondent_key: 1 }（single_response=true 时唯一）

设计理由：

- 答案内嵌在 response 中，因为统计和提交总是以“整份答卷”为单位读写；一次读取即可获得该答卷全部答案，避免多集合 join。
- 每题作答后整体更新 answers（按 question_id 去重），实现草稿式保存。
- answers 保存 question_id 和值，不重复保存题干与选项文字。发布后题目结构锁定，保证引用稳定。
- respondent_key = HMAC(服务端密钥, survey_id + ":" + user_id)，用于匿名模式下仍能执行“禁止重复提交”。该值不可逆，不在界面或统计中展示，降低身份关联风险。
- access_token_hash 防止他人仅猜到答卷 ID 就操作他人答卷；原始随机令牌放在签名会话中。
- survey_id + status 支持统计与提交数查询；survey_id + respondent_key 的部分唯一索引在数据库层保证：禁止重复填写的问卷，同一用户最多只能存在一份答卷文档，避免并发“先查后写”竞态。

## 7. Schema Validator

应用启动时 db.py 会为六个集合创建或更新 $jsonSchema 校验器，validationLevel 为 strict，validationAction 为 error。校验内容包括：

- 必填字段。
- ObjectId、string、bool、date 等 BSON 类型。
- survey 状态枚举。
- 题目类型枚举。
- 用户名和标题长度。

应用层仍然进行更细粒度的业务校验（例如跳转目标必须靠后、选项不能重复、最小值不能大于最大值），因为 JSON Schema 不适合表达跨字段和跨文档规则。

## 8. 为什么适合 MongoDB

### 8.1 题型配置差异大

单选和多选需要 options；多选需要选择数量；文本需要字数；数字需要范围。文档模型允许 validation 子文档按题型变化，不需要为每种题型建表或在关系表中塞入大量空字段。

### 8.2 跳转规则是题目的一部分

跳转规则数量少、总与题目一起读取、结构可以随条件类型变化，适合内嵌为数组。关系数据库通常需要 questions、jump_rules、jump_conditions 多张表，查询和写入成本更高。

### 8.3 答卷是天然的聚合根

一份答卷包含多道题的答案，通常整体提交、整体统计。将 answers 内嵌到 response 减少读放大，并让“每次填写都保存”成为一次文档更新。

### 8.4 统计需要灵活的聚合管道

统计需要按问卷过滤、展开答案数组、按题目分组、再按选项计数。MongoDB aggregation 的 $match、$unwind、$group 与这种数据结构直接对应。

### 8.5 仍然避免“单集合万能表”

没有把用户、问卷、题目、答卷、题库和版本全部塞进一个集合。拆分为六个集合后，各集合职责清晰、索引独立、生命周期不同，符合课程对“勿将所有数据存在一个集合”的要求。

## 9. 与关系数据库的对比

关系数据库也可以实现本系统，但需要更复杂的表结构：

- 题型配置可能被拆成多个扩展表，或在 questions 表中加入大量可空列。
- 跳转条件需要单独的 jump_rules 表，条件和目标需要多行表示。
- 答卷和答案需要 response_answers 关联表，统计时需要多表连接。
- 多选答案需要 answer_options 关联表或数组字段，关系模型下统计更繁琐。

本项目的核心是问卷结构和条件逻辑的可变配置，文档模型能更自然地表达这些一对少、结构可变的子文档。代价是跨文档一致性需要应用层保证，因此发布后锁定题目结构，并配合 Schema Validator 与唯一索引。

## 10. 一致性与扩展考虑

- 发布后锁定题目与跳转，避免新答卷与旧答卷结构混杂。
- 删除草稿题目时同步清理指向它的跳转规则，避免悬挂引用。
- 第二阶段已通过 question_bank + question_versions + questions 快照解决“修改题目影响旧问卷”的问题；后续如需支持已发布问卷换题，应新增显式的问卷修订流程，而不是直接覆盖 questions。
- 禁止重复填写已通过 `single_response=true` 的部分唯一索引下沉到数据库层；允许重复填写的问卷不受该索引限制。
- 答卷统计只读取 submitted，in_progress 草稿保留但不会进入结果。

## 11. 第二阶段新增：question_bank 与 question_versions

### 11.1 question_bank 集合

question_bank 表示“题目”的逻辑身份，一个题库题目可以被多份问卷使用，也可以共享给多个用户。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| _id | ObjectId | 题库题目主键 |
| owner_id | ObjectId | 所有者 |
| title | string | 当前版本标题，冗余用于列表展示 |
| type | enum | 当前版本题型，冗余用于列表展示 |
| current_version_id | ObjectId | 当前最新版本 |
| current_version | int | 当前最新版本号 |
| shared_with | ObjectId 数组 | 被共享用户 |
| created_at | date | 创建时间 |
| updated_at | date | 最近改版或共享时间 |

索引：

    { owner_id: 1, updated_at: -1 }
    { shared_with: 1, updated_at: -1 }

设计理由：

- 逻辑题目与具体内容分离，删除/替换版本不会改变题目身份。
- shared_with 内嵌用户 ID 数组，共享关系规模小、读取题目时总是一起使用，避免额外关联集合。
- title/type 是 current_version 的受控冗余，只用于列表快速展示；创建新版本时在同一业务流程中更新。

### 11.2 question_versions 集合

question_versions 保存题目的不可变版本。任何“修改题目”的操作都新增版本文档，不更新旧版本内容。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| _id | ObjectId | 版本主键 |
| bank_id | ObjectId | 所属题库题目 |
| version_number | int | 版本号，从 1 递增 |
| title | string | 该版本题目内容 |
| type | enum | 该版本题型 |
| required | bool | 是否必答 |
| options | array | 该版本选项 |
| validation | object | 该版本校验配置 |
| parent_version_id | ObjectId 或 null | 直接父版本；v1 为 null |
| restored_from_version_id | ObjectId 或 null | 若由恢复历史版本产生，记录被恢复的版本 |
| created_by | ObjectId | 创建该版本的用户 |
| created_at | date | 创建时间 |

索引：

    { bank_id: 1, version_number: 1 } unique
    { bank_id: 1, created_at: -1 }

设计理由：

- 版本内容不可变，历史版本天然可审计、可恢复。
- parent_version_id 表达版本演进关系；restored_from_version_id 区分“正常改版”和“恢复旧版”，因此恢复操作也能保留完整历史。
- bank_id + version_number 唯一索引在数据库层防止同一题目出现重复版本号；应用层使用 max(version_number)+1 并在唯一键冲突时重试。
- 不把 jumps 放入版本：跳转依赖问卷内其他题目和目标顺序，属于问卷编排，不是题目本身的复用内容。问卷选题时 jumps 初始化为空，由问卷自行配置。

### 11.3 为什么问卷仍保存题目快照

如果 questions 只保存 library_question_id 并在展示时实时读取 current_version，那么题库一改版，旧问卷的题干、选项和答案含义都会变化，历史答卷无法解释。因此系统在“从题库选题”时复制指定版本到 questions：

- 问卷填写、跳转、统计继续读取 questions，行为与第一阶段一致。
- 题库改版只改变 question_bank.current_version_*，不触碰任何 questions 文档。
- 不同问卷可以选择不同版本，同一题目的多个版本可以并存。
- 跨问卷统计通过 library_question_id 聚合所有相关题目快照。
- 这也保留了第一阶段的发布锁定：已发布问卷的 questions 快照不允许修改或删除。

### 11.4 权限模型

- 所有者：管理题库、创建/恢复版本、共享/取消共享、查看全部使用情况与跨问卷统计。
- 被共享用户：查看题目、在自己的草稿问卷中选题、查看自己问卷范围内的使用情况与统计、复制为自有题目。
- 被共享用户不能创建所有者题目的新版本，也不能共享该题目；越权管理返回 403。
- 未共享用户访问题目详情返回 404，避免泄露题目是否存在。
